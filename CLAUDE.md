# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AutoPedido 2.0 ("Eatsy"): self-ordering system for restaurants — touch kiosk, cashier (caja), kitchen (cocina), public "order ready" screen (llamados), customer phone tracking (seguimiento) and admin panel, all synced in real time. It is a migration of an earlier Laravel app. Code, comments, identifiers, UI text and commit messages are in **Spanish (rioplatense)** — keep that convention.

Stack: Node.js ≥ 22.13 (ESM, `"type": "module"`), Express 5, MySQL 8 / MariaDB via `mysql2`. No build step, no bundler, no TypeScript, no linter configured. Frontend is plain HTML + native ES modules; vendor libs (Bootstrap, SweetAlert2, Chart.js, JsBarcode) are served from `node_modules` under `/vendor/*` (see `VENDOR` in `src/app.js`) so the app works offline.

## Commands

```bash
npm start                 # HTTP + WebSocket on the same port (default 3000)
npm run dev               # same, restarts on changes in src/ and server.js
npm test                  # node:test, runs tests/**/*.test.js
node --test tests/websocket.test.js                          # single file
node --test --test-name-pattern="descuentos" tests/utils.test.js  # single test
npm run db:reset          # drop + recreate tables per APP_MODE (production requires `-- --confirmar`)
npm run db:demo           # add 14 days of sample orders (demo mode only)
```

Requires a running MySQL (locally usually XAMPP, root without password). Config comes from `.env` loaded with native `process.loadEnvFile` (`src/config/index.js`); see `.env.example`. `DATABASE_URL` overrides the `DB_*` vars. Tests are pure unit tests (pricing, scrypt, HMAC tokens, validator, WebSocket protocol) and do not need the database.

## Architecture

**Startup (`server.js`)**: `initDatabase()` creates the DB if missing, executes `src/db/schema.sql` (idempotent `CREATE TABLE IF NOT EXISTS`) and then `src/db/migrations.js` on every boot. If `usuarios` is empty, `seedInicial()` seeds according to `APP_MODE` (`demo` = sample catalog/users; `produccion` = empty tables + one admin). Schema changes for existing databases must be added as idempotent steps in `runMigrations` (e.g. `addColumn`), not only in `schema.sql`.

**Backend layering (`src/`)**: `routes → controllers → services → repositories → db`.
- `routes/api.routes.js` mounts everything under `/api` with `express.json`, `csrfGuard` (all mutating requests need header `X-Requested-With: fetch`; the frontend `public/js/core/api.js` adds it), `no-store` caching, and per-role `requireRole(...)`. `routes/pages.routes.js` serves HTML with clean URLs and `pageGuard` per section; `.html` paths are blocked from direct static access.
- Roles: `Administrador`, `Cajero`, `Cocina`, `Cliente` (the kiosk logs in as `Cliente`). Home per role is `HOME_BY_ROLE` in `services/auth.service.js`.
- Controllers validate input with the in-house `utils/validator.js` (`validate(input, schema)`) and throw `HttpError` helpers from `utils/http-error.js` (`badRequest`, `notFound`, `conflict`, …), handled by `middlewares/error-handler.js`. Admin CRUDs are generated by `crudController` in `controllers/helpers.js`.
- DB access: use `sql.all / sql.get / sql.run` from `db/connection.js` with `?` placeholders. `transaction(fn)` uses `AsyncLocalStorage`, so any `sql.*` call inside `fn` (even in nested repositories) automatically runs on the transaction connection; nested `transaction` calls reuse it.
- Pricing/promotions logic lives in `services/pricing.service.js` (per-unit discounts, never negative) and `services/cupones.service.js` (coded promotions = fixed-amount coupons applied to the order total). Order detail rows store unit price and discount at order time.

**Auth**: no session store. Session is an `httpOnly` cookie (`ap_session`) holding an HMAC-signed token (`utils/token.js`); passwords use scrypt (`utils/password.js`). `loadUser` re-reads the user each request so disabling a user takes effect immediately. A customer's phone gets a separate `ap_seguimiento` cookie that only allows viewing one order: `seguimientoLock` redirects pages to `/seguimiento` and the API returns 403 for anything else.

**Real time**: WebSocket is implemented by hand (RFC 6455, no library) in `src/websocket/` — `protocol.js` (frames), `connection.js`, `server.js` (handshake, Origin check, heartbeat, broadcast), mounted at `/ws` on the same HTTP server and authenticated with the session cookie. Services emit events via `publish(type, { staff, kiosco, publico, seguimiento })` from `websocket/realtime.js`: each audience gets its own payload (public screen gets masked data via DTOs, seguimiento only receives events whose `id` matches its tracked order). When adding events, decide explicitly what each audience may see. Client side: `public/js/core/realtime.js` (auto-reconnecting client).

**Frontend (`public/`)**: one HTML page per screen under `public/<section>/`, with a matching module in `public/js/<section>/` and CSS in `public/css/`. Shared modules in `public/js/core/` (`api.js` fetch wrapper with 401→login handling, `ui.js` incl. HTML escaping, `layout.js`, `ticket.js`, `sound.js`, `touch-keyboard.js`). Escape any user data inserted into HTML.

**Deployment**: `render.yaml` (Render blueprint; MySQL hosted externally, e.g. Aiven, with `DB_SSL=true`). `/api/health` is a DB-free ping for keep-alive crons; `/api/salud` checks MySQL and is Render's health check. Uploaded images go to `uploads/` (ephemeral on Render).
